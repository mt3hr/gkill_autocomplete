# 要件定義

何をどう提案するかの取り決めです。閾値と除外条件の根拠もここに書きます。

例示に出てくるタグ名・リポジトリ名はすべて架空のものです。

## 1. やること・やらないこと

| | |
| --- | --- |
| やる | まだタグの付いていない記録に対して、付けるべきタグを提案する |
| やる | 提案を保存し、人が1件ずつ承認・却下できるようにする |
| やる | 承認されたタグだけを gkill へ書き込む |
| やらない | 提案を自動で適用する |
| やらない | gkill 本体を変更する |
| やらない | クラウドの LLM を使う |
| やらない | まとめて承認する手段を用意する |

## 2. 提案の対象

次の条件をすべて満たす記録だけを対象にします。

1. 設定した範囲（リポジトリの接頭辞・記録の種別・期間）に入っている
2. タグが1つも付いていない（`exclude.already_tagged` が真の場合）
3. 人がまだ判定していない
4. まだ判定にかけていない（`--reeval` を付けた場合を除く）

### 全種別を対象にできる

`scope.rep_prefixes` と `scope.data_types` を空にすれば、全リポジトリ・全種別が対象になります。

**広げても費用は跳ねません。** タグ履歴の無い文脈では候補タグが0個になり、LLM を呼ばないためです。
`candidates.min_examples` に満たないタグしか無い文脈は、判定に入る前に打ち切られます。

時間がかかるのは「タグ履歴があり、かつ未タグの記録が残っている」文脈だけです。
写真の保管庫がこれに当たるので、最初は `scope.candidate_days` を短くして件数を見てください。

### 取得の上限

1回の解析で読む記録数には上限があります（`scope.max_scan_records`、既定60,000）。
範囲を絞らずに走らせたときの歯止めです。

**上限に達したら警告を出します。** 達すると学習が不完全なまま「正常終了」に見えてしまい、
黙って提案の質が落ちるためです。警告が出たら、範囲を絞るか `scope.learn_days` を縮めるか、
上限そのものを上げてください。

自動収集の記録まで含めると日に数百件生まれるので、全種別を対象にする場合は
`learn_days` を短めにしないと上限に届きます。

## 3. 学習

### 3.1 文脈

学習と候補抽出の単位です。

| 記録の種類 | 文脈 |
| --- | --- |
| 写真 | リポジトリ種別（`rep:SampleRep`） |
| それ以外 | 記録の種別（`type:kmemo`） |

写真だけリポジトリを使うのは、gkill の一覧取得が写真以外にリポジトリ名を返さないためです。
また写真はリポジトリごとに写すものが決まっているので、そちらのほうが文脈として適切でもあります。

リポジトリ種別はリポジトリ名の先頭部分です。gkill のリポジトリ名は「種別_端末_日付」の形なので、
端末を買い替えても同じ文脈にまとまります。

### 3.2 集計するもの

タグごとに次を数えます。

- 文脈ごとの出現数 → 候補タグの絞り込みに使う
- 時刻の分布（24分割） → 弱い事前確率に使う
- 本文の索引 → 逐語一致の照合に使う
- 参考例（本文・写真を数件） → LLM に見せる

**タグを付けなかった記録も数えます。** これを数えないと「付けない」という選択の重みが分かりません。

### 3.3 除外するタグ

`exclude.tag_patterns` に当たるタグは学習しません。末尾の `*` だけを解する前方一致です。

他のツールが取り込み時に機械的に付けたタグを候補から締め出すためのものです。混ざると件数で
圧倒され、手で付けているタグが候補から埋もれます。

### 3.4 文脈の自動選択

`gkill_autocomplete init` は次の基準で文脈を選びます。

| 判定 | 条件 |
| --- | --- |
| 対象にする | 記録が20件以上あり、2種類以上のタグを使い分けており、タグ無しが95%未満 |
| 機械付与とみなす | 1種類のタグが95%以上を占め、かつタグ無しが5%未満 |

**2種類以上のタグを使い分けている**ことを条件にしているのは、そこで人の選択が起きている印だからです。
1種類しか使われていない文脈は、機械が一律に付けているか、そもそも選択の余地がありません。

機械付与とみなした文脈の主要タグは、そのまま `exclude.tag_patterns` に入ります。

自動選択する文脈は最大8個です。

## 4. 候補タグの絞り込み

同じ文脈での実績が `candidates.min_examples`（既定5件）に満たないタグは候補になりません。
実績の多い順に `candidates.max_candidate_tags`（既定8個）まで取ります。

全タグを総当たりしないのは、選択肢が多すぎると LLM の判定が荒れるためです。文脈で絞れば
数個に収まります。

## 5. 判定の段階

上の段階で決まったら下は見ません。

| 段階 | 手段 | LLM |
| --- | --- | --- |
| 0 | 設定のルール | 不要 |
| 1 | 本文が過去の記録と逐語一致 | 不要 |
| 2 | 近傍の記録・記録自身の語との一致 | 不要 |
| 3 | LLM に候補タグの当否を尋ねる | 要 |

### 5.1 逐語一致

本文を正規化して比べます。吸収するのは次だけです。

- 前後の空白
- 改行コードの違い、空行
- 全角空白とタブ
- 英字の大小

同じ操作を繰り返して生まれる記録は字面がそのまま一致するので、これで足ります。
一致した場合、その本文に付いていた**すべてのタグ**を提案します。

### 5.2 近傍の記録

`scoring.neighbor_window_minutes`（既定5分）以内にある別の記録の見出しや本文に候補タグ名が
現れたら提案します。対になる記録が数秒差で並ぶことがあり、片方が他方の手がかりになります。

### 5.3 LLM

候補タグそれぞれについて当否を尋ねます。**「どれが最も近いか」ではなく「それぞれ当てはまるか」**です。

渡すのは次の3つだけです。

- 候補タグの名前
- 判定したい記録の中身（本文または写真）
- そのタグらしい記録の見本（本文は候補ごとに2件、写真は `candidates.max_few_shot_images` 枚まで）

**写真の見本は枚数に注意が必要です。** 写真は1枚で千数百トークンになるので、数枚添えるだけで
LLM の文脈長を超え、判定そのものが失敗します（既定の 4096 では見本3枚＋対象1枚で 7486 トークンに達しました）。

文脈長が足りない場合はその旨と直し方を出します。見本写真は「よく似ているが中身が違うもの」を
見分けるのに効くので、枚数を削るより **LLM 側の文脈長を広げるほうが望ましい**です。

**記録のID・リポジトリ名・ファイル名・保存場所は渡しません。** 写真はデータとして埋め込むので、
接続先に利用者のファイル構成を知らせることもありません。

候補に無い名前が返ってきた場合は捨てます。

## 6. 提案の確定

### 6.1 multi-label

候補タグごとに独立して当否を決めます。結果は**0個にも複数個にもなります**。

**0個は正常な答えです。** 記録の一定割合は意図的にタグを付けないまま残されます。
実データでは、ある種類の記録の約4分の1がそれに当たりました。

### 6.2 「そこでタグを付けるか」で割り引く

推測から出た確信度は当てになりません。実測では、写真の保管庫に対する LLM の判定が
**9件すべて 1.0** を返し、「〜という名前をもつ可能性があります」といった後付けの理由が
付いていました。自己申告をそのまま閾値にかけても何も濾せません。

一方「その場所でタグを付けているか」は履歴から数えられる事実です。そこで、

```
割り引いた確信度 = もとの確信度 × (1 − その文脈でタグを付けない割合)
```

とします。ほとんどタグを付けない場所では、よほど強い証拠が無い限り黙るのが正しい動きです。

**逐語一致と設定のルールは割り引きません。** 推測ではなく直接の証拠だからです。

### 6.3 閾値

`scoring.threshold`（既定 0.6）未満の提案は表に出しません。

同じタグが複数の経路から出た場合は、最も確信度の高いものだけを残します。

### 6.3 既定値の根拠

| 設定 | 既定 | 根拠 |
| --- | --- | --- |
| `scope.candidate_days` | 30 | 未確認の記録が溜まるのは数日ぶん。30日あれば取りこぼさない |
| `scope.learn_days` | 180 | 季節で記録の傾向が変わるので長めに取る。全種別を対象にする場合は上限に届くので短くする |
| `scope.max_scan_records` | 60000 | 範囲を絞らない使い方でも破綻しないところ |
| `candidates.max_few_shot_images` | 2 | 文脈長が既定(4096)のままの環境でも収まる枚数 |
| `candidates.min_examples` | 5 | これ未満は偶然の可能性が高い |
| `scoring.threshold` | 0.6 | 実測に合わせて調整する余地を残した中間の値 |
| `scoring.exact_text_match_confidence` | 0.95 | 逐語一致は極めて強い手がかり |
| `scoring.neighbor_window_minutes` | 5 | 対になる記録は数秒から数分の差で並ぶ |
| `scoring.time_of_day_weight` | 0.1 | 実測では同じタグが一日中ばらけて現れ、時刻は決め手にならなかった |

`learn_days` は `candidate_days` 以上でなければなりません。提案したい範囲より学習範囲が狭いと、
候補タグが出揃わないためです。設定の検証で弾きます。

## 7. 人の判定

| 操作 | 結果 |
| --- | --- |
| タグを選んで確定 | 選んだタグを gkill へ書き込む。選ばなかった提案は却下として畳む |
| 何も選ばずに確定 | 「この記録にタグは要らない」として記録する。二度と提案しない |

判定は**再生成できない情報**なので、派生データを掃除するときも消しません。

同じ識別子のタグが gkill に既にある場合は書き込みません。**過去に付けて手で消したタグを
蘇らせないため**です。

## 8. 個人情報

| 決まり | 実装 |
| --- | --- |
| LLM はローカル限定 | ループバック以外は起動を拒否。クラウド用の設定項目を持たない |
| 記録に触れる口はすべて認証の後ろ | 一覧・承認・解析・写真の中継 |
| 通信は暗号化する | gkill 本体と同じ証明書で TLS |
| 資格情報を保存しない | パスワードもハッシュもセッションも、ファイルに持たない |
| ログに本文を出さない | 出すのは件数と所要時間だけ |
| リポジトリに個人データを置かない | 設定・DB・ログはすべてリポジトリの外。資料と雛形は架空の値 |
| 画像をディスクに残さない | 確認画面へは中継するだけ |
| Service Worker に記録を溜めさせない | `/api` と `/thumb` は NetworkOnly。溜めるのは画面の器だけ |

**設定に資格情報を書く場所がありません。** 認証は gkill の設定ディレクトリを
直接見て行うので、パスワードもそのハッシュも渡す必要がなくなりました。
`config_test.go` が「設定の JSON に password / credential / session を含むキーが無い」ことを検査します。

## 9. 認証

### 9.1 コマンドラインは認証しない

渡すのは利用者IDだけです。gkill を叩くためのセッションは、
`$GKILL_HOME/configs/account_state.db` へ直接書いて発行します。

| 決まり | 理由 |
| --- | --- |
| 信頼の根拠は「同じ端末で設定ディレクトリに書けること」 | gkill 自身の `auto_tag` / `update_cache` と同じ手口 |
| `ApplicationName` は `"gkill"` 固定 | gkill の認証が一致を要求する。違うと全 API が弾かれる |
| セッションは1週間で、使用中は取り直す | 確認画面は何日も上がったままになる。終了時に必ず消すことで、長寿命の鍵が gkill の DB に残り続けないようにする |
| 終了時に発行したセッションを消す | gkill の DB に残り続けさせない |
| `account.db` のスキーマ版が違えば何もせず止まる | 旧版を開くと gkill 側が自動移行を走らせ、**全アカウントのパスワードが無効化される** |

### 9.2 確認画面のログイン

gkill のアカウントで入ります。**有効なアカウントなら誰でも入れます。**

判定の順序と理由は gkill の `handle_login.go` に合わせてあります。

| 順 | 条件 | |
| --- | --- | --- |
| 1 | 回数制限（IP毎・15分に5回） | 資格情報を見る前に計上する |
| 2 | アカウントが無い | 存在を教えない |
| 3 | 無効なアカウント | 照合まで行かない |
| 4 | リセットトークンが残っている | **期限に関わらず**入れない |
| 5 | パスワードが違う | 未設定は常に不一致（fail-closed） |

| 決まり | 理由 |
| --- | --- |
| 照合は手元の `account.db`。gkill の `/api/login` は叩かない | 叩くと gkill 側のログイン回数（15分に10回）を消費する。総当たりを受けたとき、**利用者自身が gkill に入れなくなる** |
| パスワードの照合は gkill のコードをそのまま使う | Argon2id のパラメータや比較の仕方がずれると、静かに弱くなる |
| ブラウザで SHA-256 にしてから送る | gkill の画面と同じ形。平文をブラウザから出さない |
| どこで弾いたかは伝えない | アカウントの存在や状態を外から探れないように |
| 失敗の応答に記録の中身を混ぜない | 未ログインの相手に断片も渡さない |

### 9.3 利用者ごとの分離

gkill では同じ人でもアカウントごとに別のリポジトリを持ちます。混ざると
**他人の記録の本文が画面に出る**ので、すべての層で分けます。

| 層 | 分け方 |
| --- | --- |
| 保存先の4表 | すべて `USER_ID` を持ち、すべての読み書きで絞る |
| 主キー | `(USER_ID, ID)` の複合。**同じ記録を複数のアカウントが見られる**ため |
| 解析 | `--user` で渡した人ぶんだけ `App` を作る |
| 写真の索引 | 利用者ごと。記録IDを知っていても他人の写真は引けない |
| 承認・解析 | 対象に含まれない利用者は 403 |

`--user` に渡されていないアカウントもログインはできますが、提案は空になります。
画面はその旨を出します（「提案が0件」と「対象外」を取り違えないため）。
