# 実装仕様

パッケージ構成、データの流れ、主要な処理の詳細です。

型と依存の向きは [class-diagrams.md](class-diagrams.md)、保存するものは
[er-diagram.md](er-diagram.md)、外に見える口は [api-endpoints.md](api-endpoints.md) にあります。

## 1. 全体像

バイナリは `gkill_autocomplete` の1本だけです。解析も確認画面の配信も同じバイナリが行います。

**どのコマンドも `--user <利用者ID>` が要ります。** パスワードは要りません。

```
gkill_autocomplete --user <利用者ID>              確認画面を開く
gkill_autocomplete --user <利用者ID> --once       解析を1回だけ行う
gkill_autocomplete init --user <利用者ID>         設定ファイルを作る
gkill_autocomplete reset --user <利用者ID>        提案を捨ててやり直せるようにする
gkill_autocomplete benchmark --user <利用者ID> --from … --to …   精度を測る
gkill_autocomplete --print-config                 既定の設定を出力する
```

## 2. `internal/config` — 設定と検証

### 2.1 未知のキーの検出

`encoding/json` は知らないキーを黙って捨てるので、綴りを間違えた設定が「書いたのに効かない」形で
通り抜けます。これを防ぐため、構造体の json タグと突き合わせて未知のキーを検出します。

`_` で始まるキーは読み飛ばします。JSON にコメントが書けないので、設定ファイル自身に説明を
書き込めるようにするための逃げ道です。

### 2.2 既定値の重ね方

既定値を入れた構造体へ上書きする方式です。書かれていないキーは既定のまま残り、書かれたキーだけが
変わります。既定が真の項目に `false` を書けば、ちゃんと偽になります。

### 2.3 外部送信の拒否

**このパッケージが唯一の関門です。** 他の場所で接続先の妥当性を判断しません。

- `llm.endpoint` がループバック（`127.0.0.1` / `::1` / `localhost`）以外なら、
  `llm.allow_remote` が明示されていない限り起動を拒否する
- `llm.thumb_size` は `400x400` の形式で各辺 1〜1024。**範囲外を渡すと gkill はエラーを返さず
  原本（全画素）を返す**ので、送る前に弾く

`server.listen` はループバック以外でも構いません。画面は gkill のアカウントによる
ログインで守られ、通信は gkill 本体と同じ証明書で暗号化されるためです。書式だけ確かめます。

問題は最初の1件で打ち切らず、すべて集めて返します。1つ直すたびに起動し直さずに済むようにするためです。

### 2.4 資格情報を持たない

設定に資格情報を書く項目は**ありません**。認証は gkill の設定ディレクトリを直接見て
行うので、パスワードもそのハッシュも渡す必要がないためです。

`config_test.go` が「設定の JSON に `password` / `credential` / `session` を含むキーが無い」
ことを検査します。うっかり項目を足したときに気づけるようにするためのものです。

### 2.5 環境変数

**環境変数のほうが設定ファイルより優先されます。**

`GKILL_HOME` / `GKILL_BASE_URL` / `GKILL_LOCALE` / `GKILL_INSECURE`

`GKILL_HOME` は gkill がプラグインを起動するときにも渡す変数なので、
gkill から起動された場合はそちらに従います。

## 2.6 `internal/gkillauth` — gkill の設定を使った認証

**gkill 本体のコードを import する唯一の場所です。** パスワードの照合を自前で書き直すと、
Argon2id のパラメータや比較の仕方がずれたときに静かに弱くなるためです。

| すること | 使うもの |
| --- | --- |
| ログインの照合 | `account.Account.VerifyPassword`（Argon2id・定数時間比較） |
| セッションの発行 | `account_state.LoginSession` + `AddLoginSession` |
| TLS 証明書の場所 | `server_config` の設定 |

### スキーマ版の確認

`account.db` を DAO で開く**前に**、書き込みを一切しない方法で版だけを読みます。

gkill のアカウント DAO は旧スキーマ（1.0.0）の DB を開いた瞬間に自動移行を走らせ、
**全アカウントのパスワードを無効化してリセットトークンを再発行します**。
このツールがうっかり先に開くと、利用者は gkill にログインできなくなります。

現行版でなければ何もせずに止まり、先に gkill を起動するよう案内します。
移行は gkill 自身にやらせるべきものです。

## 3. `internal/gkillclient` — gkill との通信

### 3.1 記録の取得

**`/api/get_kyous` ではなく `/api/get_kyous_mcp` を使います。**

`/api/get_kyous` が返す構造体は15項目だけで、本文もタイトルもタグも含みません。埋めるには
記録1件ごとに追加のリクエストが要り、ページング機構もありません。`get_kyous_mcp` なら
タグ・本文・種別ごとの中身が1回で揃い、`limit` / `cursor` でページングもできます。

カーソルが進まない応答を受けた場合は打ち切ります。無限ループを避けるためです。

### 3.2 セッション

**gkill のログインは IP ごと・15分のスライディングウィンドウで10回までです。**
資格情報の検証より前に計上され、成功したログインも1回として数えられます。

したがってセッションはファイルに保存し、プロセスを跨いで使い回します。起動のたびにログインすると
数回動かしただけで制限に掛かります。

保存したセッションが別のユーザ・別のサーバ向けだった場合は使いません。

### 3.3 再ログイン

認証エラーを受けたときだけ、1回だけ再ログインして送り直します。ネットワークエラーや
タイムアウトの再試行はしません。

再ログインの契機にするエラーは4つです。

| コード | 意味 |
| --- | --- |
| `ERR000002` | アカウントが見つからない |
| `ERR000013` | セッションが見つからない |
| `ERR000238` | アカウントが無効 |
| `ERR000373` | **セッションの期限切れ** |

最後の1つが重要です。gkill のセッションは30日で切れます。gkill 同梱の MCP 実装はこのコードを
契機に含めておらず、30日後に再ログインせず落ちます。ここでは必ず拾います。

回数制限（`ERR000374`）を受けた場合は**再試行しません**。窓を食い潰すだけで回復が遠のきます。

### 3.4 エラーの見方

gkill は業務エラーの中身を**レスポンスボディの `errors`** に入れて返します。
ステータスは `error_code` から決まりますが（gkill 側 ADR-0045）、`error_code` そのものは
本文にしかありません。**ステータスで打ち切らずに本文を読んでください。**
また**成功時の `errors` は空配列ではなく `null`** です。

ローカル限定アクセスによる拒否は `ERR000414`（HTTP 403）で見分け、同じ端末から
実行するよう案内します。403 は管理者権限なし・アカウント無効にも使われるので、
ステータスだけで決め打ちすると誤誘導になります。

### 3.5 タグの書き込み

**識別子と各時刻はサーバが補完しないので、すべてこちらで入れます。**
`related_time` を省くとゼロ値になり、時系列の表示から外れます。対象の記録の時刻を必ず入れます。

`create_app` / `update_app` には `gkill_autocomplete` を刻み、後から出所を追えるようにします。

同じ識別子のタグが既にある場合、gkill は `ERR000056` を返して何も書き込みません。これは
失敗ではなく「何もしなかった」なので、そのように扱います。

### 3.6 画像の取得

`/files/` の認証は**クッキーだけ**です。`Cookie: gkill_session_id=<セッション>` を付けます。
リクエストボディやクエリでは渡せません。

URL は「種別/ファイル名」を区間ごとにエスケープして組み立てます。ファイル名の中の `/` は
区切りとして残し、`.` と `..` は落とします。

読み込む量に上限を設けます。サムネイルの指定を誤ったときに巨大な原本を丸ごと読まないためです。

## 4. `internal/ids` — 決定的な識別子

提案の識別子とタグの識別子を、`(記録のID, タグ名)` から UUIDv5 で導きます。

用途ごとに名前空間を分けています。分けないと同じ入力から同じ値が出てしまいます。
記録のIDとタグ名の間には区切りを入れます。区切りが無いと `("ab","c")` と `("a","bc")` が
衝突します。

## 5. `internal/store` — 提案と判定の保存

SQLite 1ファイル。4つの表があります。

| 表 | 内容 | 性質 |
| --- | --- | --- |
| `SUGGESTION` | 提案 | 派生データ。解析し直せば戻る |
| `VERDICT` | 提案1件に対する承認・却下 | **再生成できない** |
| `RECORD_VERDICT` | 記録単位の「タグ不要」 | **再生成できない** |
| `EVALUATION` | 判定済みの印 | 派生データ |

`ClearSuggestions` は派生データだけを消します。判定まで消すと、却下したはずの提案が次の解析で
全部復活します。

提案を保存する前に、その提案またはその記録に人間の判定があるかを確かめます。あれば保存しません。

## 6. `internal/suggest` — 学習と判定

### 6.1 学習

統計を数えるだけで、モデルの訓練はしません。文脈ごとの出現数、時刻の分布、本文の索引、
参考例、タグ無しの数を集めます。

### 6.2 判定

段階ごとに関数が分かれています。上の段階が結果を返したら下は呼びません。

```
deniedTags()             設定で「提案しない」とされたタグを集める
suggestByRules()         設定のルール
suggestByExactText()     本文の逐語一致
candidatesFor()          候補タグの絞り込み
suggestByContext()       近傍の記録・語の一致
canSurviveHabitDamping() 呼んでも無駄かを先に見る  ← LLM の手前の関門
Classifier.Classify()    LLM
finish()                 閾値で足切りし、確信度の高い順に並べる
```

`Classifier` はインターフェースです。LLM を使う実装を差し込むための境目で、
**nil のままでも逐語一致と近傍による判定は動きます**。

#### 呼んでも無駄な LLM 呼び出しを省く

`dampenByHabit` は確信度に `keepRate = 1 − その文脈の未タグ率` を掛け、`finish` が閾値未満を
落とします。LLM の確信度は最大 1.0 なので、**割り引き後の上限は `keepRate` そのもの**です。
つまり `keepRate` が閾値に届かない文脈では、LLM が満点を返しても必ず落ちます。

`canSurviveHabitDamping` はこれを呼び出しの前に判定し、無駄だと分かっている場合は
`TierHopeless` を返して LLM を呼びません。**提案の中身は1件も変わりません。**
捨てられると分かっている答えを作る手間だけが消えます。

これが要るのは、ほとんどタグを付けていない場所の記録が件数の大半を占めるためです。
実測（2026-08-12）では判定の 61.7% が LLM に流れ、そのうち約9割が提案0個で終わっていました。
1件あたり5秒前後かかるので、16万件の判定が10日規模になっていました。

`TierHopeless` を `TierNone` と分けてあるのは、「候補が無かった」のか「呼んでも無駄だった」のかを
後から数えられるようにするためです。判定の速さはこの割合でほぼ決まります。

**`dampenByHabit` か `finish` を変えるときは `canSurviveHabitDamping` も見てください。**
割り引き方や足切りの仕方が変わると、この先読みが嘘になります。

## 7. `internal/classify` と `internal/llm`

`llm` は OpenAI 互換の `/v1/chat/completions` を叩くだけの層です。どこへ送ってよいかの判断は
しません（`config` の仕事）。

送るときに3つを必ず添えます。**いずれも「お願い」ではなく制約として効かせるためのもの**です。

| 項目 | 値 | 理由 |
| --- | --- | --- |
| `temperature` | 0 | 判定の揺れを抑える |
| `response_format` | `{"type":"json_object"}` | 文法で縛る。指示文で JSON だけを求めても従わないことがある |
| `max_tokens` | 512（`maxAnswerTokens`） | 応答が終わらなくなるのを防ぐ |

**`max_tokens` を渡さないと応答が終わらないことがあります。** 判定は temperature 0 の貪欲デコード
なので、モデルが同じ判定を繰り返し続ける状態に入りえます。上限を渡さないと llama.cpp 側は
生成長を実質無制限として扱い、文脈長を使い切るまで生成したうえで、閉じ括弧の無い JSON を返します。
`ExtractJSONObject` は対応する `}` を探すので、これは `ErrBadResponse` になります。

これは**分かりにくい壊れ方**をします。判定は失敗しても飛ばして次へ進むので画面の進捗は伸び続け、
LLM も動き続けているのに、保存される判定が1件も増えません。
`llm_test.go` の `TestCompleteConstrainsTheAnswer` が送信内容を固定して再発を防いでいます。

`classify` は問い合わせの中身を組み立て、応答を解釈します。

- 応答から最初の JSON オブジェクトを切り出す。モデルは指示しても前置きや囲いを付けてくるため、
  素直に解釈せず対応する括弧の範囲を取る
- 候補に無いタグは捨てる
- 写真はデータとして埋め込む。ファイルの場所は渡さない

## 8. `internal/app` — 全体の配線

### 8.1 解析

**取得は1回で済みます。** 学習の窓（`learn_days`）と候補の窓（`candidate_days`）は独立に
指定できますが、gkill から取ってくるのは**両者の広いほう**（`fetchDays()`）1回だけで、
あとはその記録を2通りに絞り込みます。

| | 使う記録 |
| --- | --- |
| `Learn()` | `selectLearnRecords()` が `learn_days` に入るものだけを渡す |
| 候補選び | `selectCandidates()` が `candidate_days` に入るものだけを選ぶ |
| 近傍の参照 | 取得した記録すべて。時刻順に並べたうえで二分探索で範囲を求める |

**どちらが広くても構いません。**

- 候補のほうが広い → 「昔の記録まで候補に出すが、判断は最近の習慣に沿う」
- 学習のほうが広い → 候補にしない古い記録も、タグの傾向を学ぶ材料になる

かつては `learn_days < candidate_days` を起動時に拒否していました。取得範囲が
`learn_days` だけで決まっていた頃は、候補の窓を広く書いても**黙って学習範囲ぶんしか
候補にならなかった**ためです。取得範囲を広いほうに合わせたので、この制約は要らなくなりました。

`AnalyzeReport` が取得件数と学習件数を別々に持つのはこのためです。両者が食い違うのは
正常な状態であり、同時に「取得が上限で切られた」ことに気づく手掛かりにもなります。

### 8.2 設定の生成

範囲を絞らずに読み、文脈ごとに使われ方を集計します。判定の基準は
[requirements.md](requirements.md) の 3.4 を参照してください。

**生成した設定には利用者のリポジトリ名とタグ名が入ります。** この生成物はリポジトリの外に置かれる
ものであり、ソースコードには決して焼き込みません。

## 9. `internal/websrv` — 確認画面の配信

### 9.1 API

| パス | 内容 |
| --- | --- |
| `POST /api/suggestions` | 未判定の提案を記録ごとにまとめて返す |
| `POST /api/decide` | 承認と却下を受け付ける |
| `POST /api/analyze` | 解析を始める（終わるのを待たない） |
| `GET /api/analyze/status` | 解析の進み具合と直近の結果を返す |
| `GET /thumb?target=<記録のID>` | 写真を中継する |

### 9.2 記録の中身は取り直す

提案の保存先には記録の中身を置いていません。画面に出すものはそのつど gkill から取り直します。
gkill 側で消したり直したりした結果がそのまま反映され、中身を二重に持たずに済みます。

gkill 側から消えた記録は画面に出しません。

### 9.3 画像の中継

受け取るのは**記録のIDだけ**です。リポジトリ名やファイル名を外から渡させません。
一覧を作るたびに「記録のID → 写真の場所」の対応を更新し、そこに無いものは中継しません。

取得したものはディスクに残さず、`Cache-Control: no-store` を付けます。

### 9.4 承認の処理

選んだタグだけを gkill へ書き込み、**同じ記録の残りの提案は却下として畳みます**。
そうしないと同じ記録が何度も出てきます。

1つも承認しなかった場合は「タグ不要」として記録します。

## 10. 確認画面（`src/client/`）

### 10.1 見た目の引き継ぎ

gkill 本体から次を引き継いでいます。

- 配色（`gkill_theme` / `gkill_dark_theme`）。独自色は `background-focused` と `highlight`
- **ダークテーマでは星が降り、ライトテーマでは雪が降る**
- スクロールバーをテーマ色に追従させる指定
- 通知を右上に積む指定
- アイコンフォントを woff2 だけに絞るビルド設定

### 10.2 降りものを見せる仕掛け

降りものは `z-index: -100000000` の固定要素として画面の背後に置かれます。

**`.v-layout--full-height { background-color: #0000 }` が唯一の仕掛けです。**
これが無いと Vuetify が塗る地の色に隠れて、降りものは一切見えません。

降りものの指定は `scoped` にできません。星と雪は JavaScript で作った要素なので、
`scoped` が付ける属性が乗らないためです。

タイマーは `onUnmounted` で必ず解除します。テーマの切り替えでコンポーネントが作り直されるので、
解除しないとループが積み重なって降りものが増え続けます。

gkill 本体からの変更点は2つです。**画面の大きさが変わったら星を置き直す**ことと、
**動きを減らす設定の端末では降りものを止める**ことです。

### 10.3 操作

1件ずつ大きく出して連続で捌きます。記録の一定割合はタグ不要なので、それが最短の操作になるように
してあります。

| キー | 動作 |
| --- | --- |
| `j` / `k` | 次へ / 前へ |
| `1`〜`9` | 候補タグを選ぶ（複数可） |
| `Enter` | 確定（**何も選ばなければタグ不要**） |
| `x` | タグ不要 |

文字を打っている最中と修飾キー付きでは反応しません。

確定は非同期なので、押した瞬間に一覧から外し、失敗したら戻します。同じ記録への二重確定は抑えます。
