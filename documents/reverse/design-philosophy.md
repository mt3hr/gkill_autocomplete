# 設計思想

なぜこの形になったか、何を避けたかを記録します。

「何をするか」の一覧は [usecase.md](usecase.md)、取り決めの具体は
[requirements.md](requirements.md) にあります。ここに書くのは**判断とその理由**だけです。

## 1. 動機

gkill には写真・メモ・金銭記録が日々溜まります。その多くは後から手作業でタグを付けることになり、
似た記録に似たタグを付ける作業が延々と続きます。この手作業を減らすのが目的です。

gkill には既にルールで一括タグ付けを行う仕組みがありますが、そのルールは**リポジトリ単位**です。
1つのリポジトリに複数種類のものが混ざっている場合、区別は記録の中身にしか存在しないので、
リポジトリ名を見るだけのルールでは原理的に届きません。そこが出発点です。

## 2. 書き込まない

**gkill_autocomplete は自分ではタグを書き込みません。**

判定は必ず外れます。外れた提案がそのまま記録に書き込まれると、後から探して消す羽目になります。
消す手間は付ける手間より大きいので、それでは元も子もありません。

提案を保存し、人が確認画面で承認したときだけ書き込みます。承認は1件ずつで、まとめて承認する
手段は用意していません。「全部承認」があると結局は目視を省くことになり、書き込まない意味が薄れます。

## 3. 0個も正しい答え

記録の一定割合は、意図的にタグを付けないまま残されます。実データを見ると、ある種類の記録では
4分の1ほどがそれに当たりました。

したがって判定器は**「どれも当てはまらない」を返せなければなりません**。最も確からしい1つを選ぶ
やり方（単一ラベル分類）にすると、本来タグの要らない記録にも必ず何かを提案してしまい、
確認画面で却下する手間が増えるだけになります。

同じ理由で、**確認画面では「タグ不要」が最短の操作**になるようにしてあります。何も選ばずに確定すれば
それがタグ不要の判定になります。

## 4. 却下を覚える

一度「この記録にタグは要らない」と決めたら、二度と提案しません。覚えていなければ、解析のたびに
同じ記録が蒸し返され、使い物になりません。

これを支えているのが**決定的な識別子**です。提案の識別子を (記録のID, タグ名) から計算で導くので、
何度解析し直しても同じ組み合わせには同じ値が割り当たります。却下の記録が同じ識別子で残っている限り、
その提案は復活しません。

同じ仕組みは gkill 側でも効きます。タグの識別子も決定的に導いているので、**過去に付けて手で消したタグ**を
承認によって蘇らせてしまうこともありません。gkill は既存の識別子に対して「既にある」と答えるだけで、
何も書き込まないからです。

## 5. 上の段階で決まれば下は見ない

判定は3段階で、上で決まったら下へ行きません。

同じ操作を繰り返して生まれた記録は、字面がそのまま一致します。そういう記録に対して LLM を呼ぶのは、
遅いうえに判定がぶれるだけで、何も得るものがありません。**LLM は最後の手段**です。

実データでは、手作業でタグを付けている記録のかなりの部分が第1段階（逐語一致）だけで説明できました。

## 6. 特定のタグをコードに書かない

候補タグは履歴での実績から決まります。コードにタグ名を書けば、タグを増やすたびにコードを直す
ことになりますし、そもそも他人の環境で動かなくなります。

人が決め打ちしたい場合のために設定でルールを書けるようにしてありますが、**その設定ファイル自体が
リポジトリの外**にあります。リポジトリに入るのは「実績が何件以上なら候補にする」といった構造的な
既定値だけです。

## 7. 外へ出さない

このツールは生活の記録そのもの、つまり本文と写真を扱います。

**LLM の接続先がループバック以外なら起動を拒否します。** クラウドの LLM を使うための設定項目は
そもそも用意していません。書けなければ事故は起きないからです。テレメトリも更新チェックもありません。

**確認画面には認証と TLS を掛けます。** 画面には未確認の提案、つまり記録の中身がそのまま
並びます。記録に触れる口は1つ残らずログインの後ろに置き、通信は gkill 本体と同じ証明書で
暗号化します。**見えるのはログインした本人の記録だけです。**

**Service Worker に記録を溜めさせません。** 画面は PWA ですが、溜めてよいのは器
（JS/CSS/フォント/アイコン）だけで、`/api` と `/thumb` は素通しにします。溜めると
ログアウトしても端末に残り、端末を共有していれば他の人からも読めてしまうためです。
そのぶんオフラインでは中身が出ませんが、それでよいと判断しました。

**ログに本文を出しません。** 出すのは件数と所要時間だけです。

**リポジトリに個人データを入れません。** 資料の例示・テストの材料・設定の雛形はすべて架空の値です。

## 8. 資格情報を持たない

**設定にパスワードを書く場所がありません。** 渡すのは利用者IDだけです。

gkill を叩くためのセッションは、gkill の設定ディレクトリへ直接書いて発行します。
gkill 自身の `auto_tag` や `update_cache` が使っている手口で、**信頼の根拠は
「gkill と同じ端末で設定ディレクトリに書けること」**です。

これには実務上の利点があります。定期実行に登録するとき、秘密を置く必要がありません。
以前は環境変数でハッシュを渡していましたが、それは「これ単体でログインできる
パスワード等価物」であり、タスクスケジューラの設定に残る形でした。

## 9. gkill 本体を変えない

gkill_autocomplete は **gkill 本体を1行も変更しません**。

理由は2つあります。1つは、このツールがローカル LLM という実行時の依存を持ち込むこと。
gkill に同梱すると「gkill を入れれば動く」という期待が壊れます。もう1つは、新しい概念を
必要としないこと。扱うのは既存のタグだけなので、gkill 側に足すものがありません。

ただし**認証だけは gkill のコードを import して使います**。パスワードの照合を自前で
書き直すと、Argon2id のパラメータや比較の仕方がずれたときに**静かに弱くなる**種類の
間違いになるためです。「変更しない」と「写し取らない」は両立します。

この判断は、同じく gkill の API だけを使う既存の衛星リポジトリと同じ形です。

## 9. 設定は読めるようにする

JSON にはコメントが書けないので、**`_` で始まるキーを読み飛ばす**ようにしました。
設定ファイル自身に説明を書き込めます。

逆に、`_` で始まらない**未知のキーはエラーにします**。綴りを間違えた設定が「書いたのに効かない」
形で通り抜けるのを防ぐためです。既定値を確かめたいときは `--print-config` で出力できます。

## 10. 避けたこと

| 避けたこと | 理由 |
| --- | --- |
| 自動でタグを付ける | 外れた提案を後から探して消す手間のほうが大きい |
| 単一ラベル分類 | タグの要らない記録にも必ず何かを提案してしまう |
| 全タグを総当たりで LLM に問う | 選択肢が多すぎて判定が荒れる。文脈で絞れば数個に収まる |
| 埋め込みの索引や学習済みモデル | 参考例を数件見せるだけで足りる。持つと更新の面倒が増える |
| クラウド LLM への対応 | 記録の本文と写真が外へ出る。設定項目を作らないことが最も確実な防御 |
| 記録の中身を自分の保存先に写す | 画面に出すものは gkill から取り直せばよい。重複して持つと消し忘れる |
| まとめて承認 | 目視を省くことになり、書き込まない設計の意味が薄れる |
