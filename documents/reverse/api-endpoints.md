# APIエンドポイント一覧

2種類あります。**自分が生やす口**（確認画面向け）と、**gkill から借りる口**です。

## 1. 自分が生やす口（全 **7件**）

すべて `internal/websrv` で定義しています。配信元は起動したこのプロセス自身です。

| メソッド | パス | 認証 | 用途 |
| --- | --- | --- | --- |
| POST | `/api/login` | 不要 | gkill のアカウントで入る |
| POST | `/api/logout` | 不要 | ログイン状態を捨てる |
| GET | `/api/session` | 不要 | ログイン済みかを返す。画面の出し分けに使う |
| POST | `/api/suggestions` | **要** | 未判定の提案を記録ごとにまとめて返す |
| POST | `/api/decide` | **要** | 承認・却下・タグ不要を受け付ける |
| POST | `/api/analyze` | **要** | 解析を始める（終わるのを待たない） |
| GET | `/api/analyze/status` | **要** | 解析の進み具合と直近の結果を返す |
| GET | `/thumb` | **要** | 写真を gkill から中継する |
| GET | `/*` | 不要 | 埋め込んだ確認画面を配信する |

**記録の中身に触れる5つはすべて認証の後ろにあります。** 1つでも漏れると、
そこから全部読めてしまいます。

### 応答の共通事項

| 事項 | 内容 |
| --- | --- |
| 文字コード | `application/json; charset=utf-8` |
| キャッシュ | すべて `Cache-Control: no-store`。記録の中身をブラウザに残さない |
| 失敗の形 | `{"error": "..."}` |
| 未ログイン | HTTP 401。**本文に記録の中身を混ぜない** |

---

### POST `/api/login`

```jsonc
// リクエスト
{
  "user_id": "someone",
  // 平文パスワードの SHA-256 を小文字16進64桁にしたもの。
  // ブラウザの中で crypto.subtle を使って作る。平文はブラウザから出ない。
  "password_sha256": "0123...（64桁）"
}
```

```jsonc
// 応答（200）
{ "ok": true, "user_id": "someone" }
```

**照合は手元の `account.db` に対して行い、gkill の `/api/login` は叩きません。**
叩くと gkill 側のログイン回数（IP毎・15分に10回）を消費してしまい、
この画面が総当たりを受けたときに利用者自身が gkill へ入れなくなるためです。

成功するとクッキー `gkill_autocomplete_session` が返ります
（`HttpOnly` / `SameSite=Lax` / TLS のときだけ `Secure` / 1週間）。

| 状態 | コード | 応答 |
| --- | --- | --- |
| 成功 | 200 | `{"ok": true, "user_id": ...}` |
| 資格情報が違う | 401 | 「利用者IDかパスワードが違います」 |
| アカウントが無効 | 401 | **同じ文面** |
| パスワードリセット中 | 401 | **同じ文面** |
| 試行が多すぎる | 429 | 「15分ほど待ってからやり直してください」 |
| 照合に失敗 | 500 | 「アカウントを確認できませんでした」 |

**どこで弾かれたかは返しません。** アカウントの存在や状態を外から探れないようにするためです。
理由はログにだけ残ります。

判定の順序は gkill の `handle_login.go` に合わせてあります
（回数制限 → 有無 → 有効か → リセット中か → パスワード）。

---

### GET `/api/session`

```jsonc
// 未ログイン
{ "authenticated": false }

// ログイン済み
{
  "authenticated": true,
  "user_id": "someone",
  // 起動時に --user で渡されたかどうか。
  // 偽なら、ログインはできても提案が無い。
  "analyzable": true
}
```

`analyzable` があるおかげで、画面は「提案が0件」と「そもそも対象外」を出し分けられます。

### POST `/api/suggestions`

リクエストは空の JSON です。**見えるのはログインした本人の提案だけです。**

```jsonc
{
  "records": [
    {
      "target_id": "…",
      "data_type": "kmemo",
      "related_time": "2020-06-01T08:00:00Z",
      "is_image": false,
      "thumb_url": "",              // 写真のときだけ "/thumb?target=…"
      "file_name": "",              // ファイルの記録(idf)のときだけ
      "text": "記録の本文",
      "existing_tags": ["タグA"],   // すでに付いているタグ
      "suggestions": [
        { "id": "…", "tag": "タグB", "confidence": 0.82, "tier": "text_match", "reason": "…" }
      ]
    }
  ],
  "pending": 12
}
```

記録の中身は保存先に置いていないので、**そのつど gkill から取り直します**。
gkill 側で消えた記録は、この一覧から静かに落ちます。

解析対象でない利用者には、空の一覧（`records: []`, `pending: 0`）を返します。

呼ばれるたびに、その利用者の**写真の索引**を作り直します。`/thumb` はこの索引しか見ません。

---

### POST `/api/decide`

```jsonc
{
  "target_id": "…",
  "approve_tags": ["タグA"],   // 空配列なら「タグ不要」
  "no_tag_needed": true        // approve_tags が空のときに真
}
```

```jsonc
{ "approved": 1, "rejected": 1, "pending": 10 }
```

**選ばれなかった提案は、同じ記録のぶんがまとめて却下になります。**
そうしないと同じ記録が何度も出てきます。

1つも承認しなかった場合は「この記録にタグは要らない」として記録し、
**次の解析でその記録には新しい提案を出しません**（タグ名が違っても出しません）。

承認したタグは gkill の `/api/add_tag` へ書き込みます。同じ識別子のタグが
既にある場合（過去に付けて手で消した記録）は、**書き込まずに承認だけ記録します**。

| 状態 | コード |
| --- | --- |
| 成功 | 200 |
| `target_id` が無い | 500（`{"error": "target_id がありません"}`） |
| 解析対象でない利用者 | **403** |

---

### POST `/api/analyze`

リクエストは空です。解析を**始めるよう頼むだけ**で、終わるのを待ちません。
中身は [usecase.md](usecase.md) の UC-10 〜 UC-15 です。

**解析はリクエストの寿命から切り離してあります。** 写真の判定は1件で数分かかり、
数十件あれば1時間を超えます。要求の文脈（`r.Context()`）に縛ると、タブを閉じる・
再読込する・端末が眠るだけで解析が死にます。解析の寿命は待ち受けの文脈で、
Ctrl+C のときだけ止まります。

応答は `GET /api/analyze/status` と同じ形です。

**二重起動は利用者ごとに防ぎます。** すでに動いていても失敗にはせず、
いまの進み具合を返します。別の人の解析までは止めません。

| 状態 | コード |
| --- | --- |
| 受け付けた / すでに動いている | 200 |
| 解析対象でない利用者 | **403** |

---

### GET `/api/analyze/status`

いまの進み具合と、直近の解析の結果を返します。

```jsonc
{
  "running": true,
  "done": 12,          // 判定を終えた記録の数
  "total": 40,         // 判定する記録の総数(決まる前は 0)
  "report": null,      // 走っている間は null
  "pending": 30
}
```

終わっていれば `report` が入ります。

```jsonc
{
  "running": false,
  "done": 40,
  "total": 40,
  "report": {
    "LearnedRecords": 32917,
    "CandidateRecords": 1905,
    "SuggestedRecords": 12,
    "NoSuggestionRecords": 30,
    "StoredSuggestions": 18,
    "SkippedByVerdict": 2,
    "FailedRecords": 3,
    "FailureReason": "LLM に繋がらない (起動しているか、設定の llm.endpoint が合っているかを確かめてください)",
    "Elapsed": 123456789
  },
  "pending": 30
}
```

`FailedRecords` は判定に失敗して飛ばした記録の数です。**0でなくても解析は完走しています。**
LLM の時間切れ・応答の解釈失敗・写真が取れない、はどれも実際に起きるので、
1件のために残り全部を捨てないようにしてあります。飛ばした記録は評価済みにしないので、
次の解析でやり直されます。

`FailureReason` は最も多かった失敗の理由です。**決め打ちの文字列しか入りません。**
エラー本文には LLM の応答や記録の中身が混ざりうるので、そのままは載せません。
これが無いと、全件失敗しても件数しか分からず原因に辿り着けません。
LLM を起動し忘れたまま走らせると、判定する記録がすべて失敗します。

解析そのものが落ちた場合は `failure` に理由が入ります。

**理由を `error` というキーで返してはいけません。** 画面側の共通処理がその名前を
「要求そのものが失敗した」と解釈するので、解析の失敗とリクエストの失敗が混ざります。

| 状態 | コード |
| --- | --- |
| 成功 | 200 |
| 解析対象でない利用者 | 200（すべて空） |

---

### GET `/thumb?target=<記録ID>`

写真を gkill から取り寄せて中継します。

**受け取るのは記録のIDだけです。** リポジトリ名やファイル名を外から渡させないので、
一覧に出ていない場所のファイルを読ませることはできません。

索引は**利用者ごと**なので、他人の一覧に載っている写真は記録IDを知っていても引けません。

| 状態 | コード |
| --- | --- |
| 成功 | 200（画像。`Cache-Control: no-store`） |
| `target` が無い | 400 |
| 索引に無い / 解析対象でない | 404 |
| gkill から取れない | 502 |

取得したものは**ディスクに残しません**。

## 2. gkill から借りる口（全 **5件**）

gkill 本体には一切変更を加えていません。使うのは次だけです。

| メソッド | パス | 用途 |
| --- | --- | --- |
| POST | `/api/get_kyous_mcp` | 記録の取得（本文・タグ・種別ごとの中身つき） |
| POST | `/api/get_all_tag_names` | タグ名の一覧（`init` が使う） |
| POST | `/api/get_all_rep_names` | リポジトリ名の一覧（接頭辞の展開に使う） |
| POST | `/api/add_tag` | **唯一の書き込み**。承認したときだけ叩く |
| GET | `/files/{rep}/{file}?thumb=WxH` | サムネイルの取得 |

**`/api/login` は叩きません。** セッションは gkill の設定ディレクトリへ直接書いて発行します
（[operations-guide.md](operations-guide.md) 2章）。

### 呼び出しで踏みやすい穴

gkill 同梱の MCP 実装を雛形にすると踏む穴があります。

| 穴 | 正しいやり方 |
| --- | --- |
| `/api/get_kyous` は本文もタグも返さず、ページングも無い | **`/api/get_kyous_mcp` を使う** |
| セッション期限切れ `ERR000373` を取り直しの契機に含めていない | **必ず含める**。含めないと期限を跨いだ瞬間に落ちる |
| `add_tag` で `related_time` を省くとゼロ値（`0001-01-01`）になる | **対象記録の時刻を必ず入れる**。省くと時系列の表示から外れる |
| `?thumb=WxH` の範囲外はエラーにならない | **各辺 1〜1024**。範囲外だと原本（全画素）が返る |
| `?thumb=` は画像以外にもエラーを返さない | 拡張子がサムネイルの対象でなければ、**原本をそのまま 200 で返す**（動画・書庫・書類のいずれでも起きる）。**応答の `Content-Type` が `image/` で始まるかを必ず確かめる**。確かめないと、動画1本を読み取り上限まで読み込むことになる |
| `idf` は画像とは限らない | `payload.is_image` を見る。偽の `idf` は写真も本文も持たないので、画面には `file_name` を出さないと空の札になる |
| `/files/` の認証はクッキーのみ | `Cookie: gkill_session_id=<id>` が要る。ボディやクエリでは渡せない |
| 業務エラーが HTTP 200 で返る | `errors` 配列を見る。**成功時は `[]` ではなく `null`** |
| `query.ids` に何千件も渡すと、エラーではなく**空の結果**が返る | **500件ずつに割って渡す**。詳細は下記 |

### `query.ids` は必ず分割して渡す

`query.ids` に渡せる記録IDには**実質的な上限があり、超えてもエラーになりません**。

gkill の Mi 検索は5射影（作成・チェック・期限・開始・終了）の `UNION` で、
**5本それぞれに `ID IN (…)` の一覧を丸ごと展開します**
（`dao/reps/mi_repository_sqlite3_impl.go`）。
バインド変数は `5N + 5` になり、SQLite の上限 32766 を **N = 6553 で超えます**。

実測（2026-08-18・稼働中の gkill に対して境界を挟んで確かめたもの）:

| 渡したID数 | 結果 |
| --- | --- |
| 6552 | `total_count=6552`。正常 |
| 6553 以上 | `total_count=0`・`errors: null`・**エラー無しで返る** |

エラーにならないのは、`handle_get_kyous_mcp.go` が
「`err` はあるが `GkillError` は無い」場合にレスポンスへ何も積まないまま返すためです
（`err` は Debug レベルのログにしか出ません）。
呼び出し側からは「成功・該当0件」と区別が付きません。

このため `websrv.fetchRecords` は `fetchRecordsChunkSize`（500件）ずつに割って問い合わせます。
回帰は `internal/websrv/suggestions_fetch_test.go` が固定しています。

### ページングの既定値

`/api/get_kyous_mcp` は `limit` と `cursor` を取ります。

| 値 | 既定 | 理由 |
| --- | --- | --- |
| `limit` | 1000 | gkill 側の上限。200 にすると3万件で153往復になり、30分を超える |
| `max_size_mb` | 16 | 1回の応答の上限 |

取得の総数には `scope.max_scan_records`（既定 60000）の歯止めがあり、
**達したら警告を出します**。黙って学習が欠けると、提案の質が静かに落ちるためです。

### 認証エラーの扱い

次のコードを受けたら、セッションを捨てて取り直し、**1回だけ**送り直します。

| コード | 意味 |
| --- | --- |
| `ERR000002` | アカウントが見つからない |
| `ERR000013` | セッションが見つからない |
| `ERR000238` | アカウントが無効 |
| `ERR000373` | セッションの期限切れ |

繰り返さないのは、gkill の DB へセッションを書き続けることになるためです。

### 成功として扱うエラー

| コード | 意味 | 扱い |
| --- | --- | --- |
| `ERR000056` | 同じIDのタグが既にある | **成功**。「何もしなかった」として承認だけ記録する |

決定的な識別子を使うので、再承認と「手で消したタグ」で必ず起きます。
どちらも**蘇らせないのが正しい**動きです。
