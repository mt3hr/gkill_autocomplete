# エラーハンドリングとセキュリティ

## 1. 方針

このツールは生活の記録そのもの（本文・写真・タグ）を扱います。
**エラーの出し方も、その一部です。** 直し方を伝えることと、
中身を漏らさないことを同時に満たす必要があります。

| 場面 | 方針 |
| --- | --- |
| 設定の誤り | **問題を全部集めて**返す。1つ直すたびに起動し直さずに済むように |
| 直せる誤り | **直し方まで書く**。素のエラー文だけでは何をすればよいか分からない |
| 認証の失敗 | **どこで弾いたかを伝えない**。理由はログにだけ残す |
| 記録に関わる失敗 | 画面には出すが、**ログには要約しか出さない** |
| 壊すと取り返しがつかない操作 | **やる前に確かめて、駄目なら何もせず止まる** |

## 2. 起動時に止まるもの

いずれも「動き始めてから困る」より「動かないほうがまし」と判断したものです。

| 条件 | 出るもの |
| --- | --- |
| `--user` が無い | 利用者の指定を求める。パスワードが要らないことも書く |
| LLM の接続先がループバックでない | 記録を外へ出さないための拒否だと説明する |
| `llm.thumb_size` が範囲外 | 各辺 1〜1024。範囲外だと gkill が原本を返すと説明する |
| `candidate_days` / `learn_days` が0以下 | 1以上にするよう説明する。**両者の大小は問わない**（どちらが広くても成り立つ） |
| 設定に知らないキーがある | 綴りの確認と、`_` で始めればコメントになることを伝える |
| **`account.db` のスキーマ版が違う** | **何もせず**、先に gkill を起動するよう案内する |
| `account.db` が無い | パスを添えて、gkill を起動するよう案内する |
| 有効なデバイス設定が無い | `server_config.db` のパスを添える |
| TLS の証明書が無い | 証明書と鍵のパスを添え、gkill の設定画面で作り直すよう案内する |
| アカウントが無い / 無効 | 利用者IDを添える |

### スキーマ版の検査だけが特別な理由

gkill のアカウント DAO は**旧スキーマの DB を開いた瞬間に自動移行を走らせ、
全アカウントのパスワードを無効化してリセットトークンを再発行します**。

このツールがうっかり開くと、利用者は gkill にログインできなくなります。
**移行は gkill 自身にやらせるべきもの**なので、こちらは触りません。

検査は DAO を通さず、`sql.Open` と1回の `SELECT` だけで行います。
DAO のコンストラクタが移行の入口だからです。`sql.Open` はファイルが無ければ
作ってしまうので、先に `os.Stat` で実在も確かめます。

## 3. 直し方まで書くエラー

素のエラー文では何をすればよいか分からないものだけ、案内を足しています。

| 症状 | 元のエラー | 添える案内 |
| --- | --- | --- |
| gkill が TLS なのに平文で繋いだ | `Client sent an HTTP request to an HTTPS server` | `base_url` を空にすれば自動で合うこと。手で書くなら `insecure_skip_verify` も要ること |
| gkill が平文なのに TLS で繋いだ | `server gave HTTP response to HTTPS client` | `base_url` を空にするか `http://` にすること |
| 自己署名証明書 | `x509: ...` | `insecure_skip_verify: true` を設定すること |
| 繋がらない | `connection refused` | gkill が動いているか、接続先が合っているか |
| HTTP 403 | — | gkill 側のローカル限定アクセス。同じ端末から実行すること |
| LLM の文脈長が足りない | `context length` 系 | 見本写真を減らすか、LLM 側の文脈長を広げること |
| 取得が上限に達した | — | 範囲を絞るか `learn_days` を縮めるか、上限を上げること |

**最後の1つは「エラー」ではなく警告です。** 上限に達すると学習が不完全なまま
「正常終了」に見えてしまい、黙って提案の質が落ちます。それが一番まずいので、
件数と直し方を出します。

## 4. gkill が返すエラーコード

業務エラーは **HTTP 200 + `errors` 配列**で返ります。HTTP ステータスだけを見てはいけません。
**成功時の `errors` は空配列ではなく `null`** です。

| コード | 意味 | 扱い |
| --- | --- | --- |
| `ERR000002` | アカウントが見つからない | セッションを取り直して1回だけ再送 |
| `ERR000013` | セッションが見つからない | 同上 |
| `ERR000238` | アカウントが無効 | 同上 |
| `ERR000373` | セッションの期限切れ | 同上。**gkill 同梱の MCP 実装はこれを漏らしている** |
| `ERR000056` | 同じIDのタグが既にある | **成功として扱う**。何もしなかったと記録する |

取り直しは**1回だけ**です。繰り返すと gkill の DB へセッションを書き続けることになります。

`ERR000056` を成功にしているのは、決定的な識別子を使う以上、
再承認と「手で消したタグ」で必ず起きるためです。どちらも**蘇らせないのが正しい**動きです。

## 5. 確認画面の応答

| 状態 | コード | 本文 |
| --- | --- | --- |
| 未ログイン | 401 | 「ログインしてください」。**記録の中身を混ぜない** |
| 資格情報が違う | 401 | 「利用者IDかパスワードが違います」 |
| 解析の対象でない | 403 | 「このアカウントは解析の対象に含まれていません」 |
| ログイン試行が多い | 429 | 「15分ほど待ってからやり直してください」 |
| 写真が索引に無い | 404 | 「その記録の写真は一覧にありません」 |
| gkill から写真を取れない | 502 | 「写真を取得できませんでした」 |
| その他 | 500 | エラー文（**ログには要約しか出さない**） |

すべての応答に `Cache-Control: no-store` を付けます。

### 401 に中身を混ぜない

未ログインの応答に記録の断片が混ざると、認証の意味がありません。
テストで固定しています（`TestUnauthenticatedRequestLeaksNothing`）。

## 6. 認証

### 6.1 判定の順序

gkill の `handle_login.go` に合わせてあります。

| 順 | 条件 | 応答 |
| --- | --- | --- |
| 1 | 回数制限（IP毎・15分に5回） | 429 |
| 2 | アカウントが無い | 401 |
| 3 | 無効なアカウント | 401 |
| 4 | リセットトークンが残っている | 401（**期限に関わらず**） |
| 5 | パスワードが違う | 401 |

**2〜5 の文面はすべて同じです。** 違えると、アカウントの存在や状態を
外から探れてしまいます。理由は `DenyReason` としてログにだけ残します。

回数制限を最初に置くのは gkill と同じで、**資格情報を見る前に計上する**ためです。

### 6.2 gkill の `/api/login` を叩かない

叩くと gkill 側のログイン回数（IP毎・15分に10回）を消費します。
この画面が総当たりを受けると、**利用者自身が gkill へログインできなくなります**。

照合は手元の `account.db` に対して行うので、ここが何度失敗しても
gkill には入れます。

### 6.3 パスワードの照合を写経しない

`account.Account.VerifyPassword` をそのまま使います。Argon2id のパラメータや
比較の仕方がずれると、**静かに弱くなる**種類の間違いになります。

保存されている値は `Argon2id(SHA-256(平文))` です。画面はブラウザの中で
SHA-256 にしてから送るので、**平文はブラウザから出ません**。

`crypto.subtle` が使えない接続では、平文を送らずに理由を出して止めます。

### 6.4 コマンドラインは資格情報を受け取らない

セッションは `account_state.db` へ直接書いて発行します。
**信頼の根拠は「gkill と同じ端末で設定ディレクトリに書けること」**です。

利点は2つあります。

- 定期実行に登録するとき、秘密を置く必要がない
- gkill 側のログイン回数を一切消費しない

## 7. 利用者ごとの分離

**このアプリで一番まずい壊れ方は「他人の記録の本文が画面に出る」ことです。**
gkill では同じ人でもアカウントごとに別のリポジトリを持ちます。

| 層 | 分け方 |
| --- | --- |
| 保存先の4表 | すべて `USER_ID` を持ち、すべての読み書きで絞る |
| 主キー | `(USER_ID, ID)` の複合。**同じ記録を複数のアカウントが見られる**ため |
| 解析 | `--user` で渡した人ぶんだけ `App` を作る |
| 写真の索引 | 利用者ごと。記録IDを知っていても他人の写真は引けない |
| 承認・解析 | 対象に含まれない利用者は 403 |

利用者IDが空のまま保存先を触ると `ErrEmptyUserID` で弾かれます。
空を許すと、その行はどの利用者からも見えない迷子になるか、
逆に条件次第で他人に見えてしまいます。

## 8. 外へ出さない

| 決まり | 実装 |
| --- | --- |
| LLM はローカル限定 | ループバック以外は起動を拒否。**クラウド用の設定項目を持たない** |
| LLM に渡すのは最小限 | 候補タグ名・対象の本文か写真・少数の参考例だけ。ID・リポジトリ名・ファイル名・位置情報は渡さない |
| 通信は暗号化 | gkill 本体と同じ証明書で TLS |
| 資格情報を保存しない | パスワードもハッシュもセッションも、ファイルに持たない |
| 写真をディスクに残さない | 確認画面へは中継するだけ |
| Service Worker に溜めさせない | `/api` と `/thumb` は `NetworkOnly` |
| ログに本文を出さない | 出すのは件数と所要時間だけ |
| リポジトリに個人データを置かない | 設定・DB はリポジトリの外。資料と雛形は架空の値 |

**書けなければ事故は起きません。** クラウド LLM の API キー項目を
設定スキーマに用意していないのは、そのためです。

## 9. ログに出すもの

| 出す | 出さない |
| --- | --- |
| 件数、所要時間 | 記録の本文、タイトル |
| 利用者ID、失敗の理由（`DenyReason`） | ファイル名、リポジトリ名 |
| エラーの種類 | LLM へ送ったプロンプト |
| 接続先（設定に書いたもの） | パスワード、セッションID |

エラー本文には記録の中身が混ざりうるので、**画面には出してもログには要約しか出しません**。

gkill から受けた失敗の応答は、読む量を 512 バイトに絞ります。
記録の本文が丸ごとログへ流れるのを防ぐためです。

## 10. テストで固定していること

| 守っていること | 場所 |
| --- | --- |
| 外部の LLM 接続先で起動を拒否する | `internal/config` |
| 設定に資格情報を書く項目が存在しない | `internal/config` |
| LLM へ記録のID・リポジトリ名・ファイル名を渡さない | `internal/classify` |
| 未ログインでは記録に触れる口が全て塞がる | `internal/websrv` |
| 未ログインへの応答に記録の中身が混ざらない | `internal/websrv` |
| 弾いた理由が応答に漏れない | `internal/websrv` |
| 無効・未設定・リセット中で入れない | `internal/gkillauth`、`internal/websrv` |
| 旧スキーマの `account.db` を開かずに止まる | `internal/gkillauth` |
| 他人の提案が見えない | `internal/store`、`internal/websrv` |
| 写真の索引が利用者ごとに分かれている | `internal/websrv` |
| `/api/login` を一度も叩かない | `internal/gkillclient` |

一覧は [testing-guide.md](testing-guide.md) にあります。
